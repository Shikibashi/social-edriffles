# WP-002 — Normalize private XRPC response headers

## Outcome

Every private `org.radlib.private.*` response, including authentication failures, carries `Cache-Control: private, no-store` and a `Vary` value that covers the authorization mechanisms accepted by the route. The PDS remains safe even if the Cloudflare edge configuration changes.

## Evidence and assumptions

- `privateAuth` currently reapplies private headers around authorization; `privateControlAuth` does not reapply them after service-auth falls through to local authorization.
- Live `listCommunities` unauthorized response was `cache-control: private`; live `getSpace` correctly returned `private, no-store`. Cloudflare reported `DYNAMIC`, so this is hardening rather than evidence of an observed cache leak.
- The response body and XRPC error types are not redesigned here.

## Scope

- Own the same API file as WP-001, hence the explicit dependency.
- Centralize/reuse the existing `setPrivateResponseHeaders` behavior across service-auth success, service-auth failure followed by authorization, authorization success, and authorization failure.
- Preserve `Vary: Authorization, DPoP` as the minimum private variation; tolerate framework-added values such as `Accept-Encoding`.
- Cover at least `listCommunities`, `getSpace`, and one `privateControlAuth` endpoint.
- Do not add a Cloudflare cache rule or change public Pages caching in this workpack.

## Tests written first

Create `upstream/atproto-pds/packages/pds/tests/radlib-private-headers.test.ts` before implementation. The test must exercise the real PDS HTTP handler and assert:

1. unauthenticated `listCommunities` 401 has exact `cache-control: private, no-store` and `Vary` contains `Authorization` and `DPoP`;
2. authenticated `listCommunities` 200 has the same private headers;
3. unauthenticated `getSpace` 401 retains the same headers;
4. a control endpoint that tries service-auth then local authorization retains the same headers on both failure and success paths;
5. a response with framework-added `Accept-Encoding` still satisfies the authorization variation invariant.

Expected red result before implementation: the service-auth fallback case and the current live-shaped unauthorized `listCommunities` response can lack `no-store` or DPoP variation.

## Implementation

1. Reuse `setPrivateResponseHeaders`; make the wrapper apply it before and after each auth attempt, including the fallback branch and caught failure.
2. Keep `json()` response headers unchanged and verify that handler-level headers cannot be overwritten by an error path.
3. Avoid a broad global cache policy change; limit this patch to the fork’s private XRPC boundary.

## Acceptance

- The new header suite passes for 401 and 200 cases.
- The focused PDS suite from WP-001 remains green.
- `python3 scripts/validate_contract.py` passes after generated/source changes.
- A read-only post-deploy probe must verify both an unauthorized and authorized private XRPC response; `cf-cache-status: DYNAMIC` is evidence only, not the acceptance condition.

## Risks and stop conditions

- Stop if the test harness cannot expose response headers without inspecting credentials or browser storage.
- Stop if a framework error handler overwrites the headers after the private auth wrapper; fix the PDS boundary or add a narrowly scoped error middleware, not a Cloudflare-only workaround.
- Do not change public community-page caching or add credentials to cache keys.

## Handoff

After green tests and diff review, hand off the exact header matrix and read-only probe commands to WP-004. Production deployment remains separately authorized.
