# WP-004 — Alpha documentation and release gate

## Outcome

The repository and release checklist accurately state what the implementation proves and what Spaces alpha still does not guarantee. A reviewer can verify the anti-block, Lexicon, and header work without treating the live hostname as a confidential production service.

## Evidence and assumptions

- Existing documents already label Spaces alpha as test-only and no-E2EE; update their acceptance rows rather than creating a parallel policy document.
- Existing audit evidence is in `.omc/research/spaces-alpha-gap-audit-20260823`; it is run-local evidence, not durable protocol memory.
- The official alpha announcement warns against production use and real-account migration; the Permissioned Data proposal describes self-contained credentials, scoped collections, notification behavior, and admitted moderation readers.

## Scope

- Update `docs/SPACES_ALIGNMENT_AUDIT.md`, `docs/SPACES_ALIGNMENT_ACCEPTANCE.md`, and `docs/SPACES_ALPHA_INTEGRATION.md` with:
  - no production/no E2EE boundary;
  - delayed revocation of already-issued credentials;
  - fail-closed remote block behavior and its bounded limitations;
  - `org.radlib.community` Lexicon/authority resolution status;
  - `private, no-store` header invariant and live probe commands;
  - explicit deferral of private AppView/search/notifications/moderation-reader services.
- Keep the documents consistent with actual test output and mark external authority publication or live deployment evidence `PENDING`/`UNVERIFIED` when not available.

## Tests written first

No source test is appropriate. The release gate is:

1. `python3 scripts/validate_contract.py`;
2. `python3 scripts/check_upstream.py --fast`;
3. focused PDS/client suites from the preceding workpacks;
4. read-only probes of an unauthorized and authorized private XRPC response, checking `private, no-store` and `Vary`;
5. manual review that no production deployment or real account mutation occurred.

## Implementation

1. Update existing status tables and residual-risk sections; do not rewrite unrelated product documentation.
2. Link the official primary sources and the exact verification commands.
3. Keep operational owner acceptance separate from automated pass/fail claims.

## Acceptance

- All three documents agree on alpha/no-E2EE and delayed-revocation limits.
- Every claim marked PASS maps to a test or read-only probe; unresolved authority/deployment items remain visibly pending.
- Contract validation passes and the documentation diff contains no credentials, tokens, private browser state, or live account data.

## Risks and stop conditions

- Stop if documentation would claim production readiness, immediate revocation, E2EE, or complete private AppView/search behavior.
- Stop if live probes require credentials or mutate data; use a disposable owner-run walkthrough later.

## Handoff

This is the final pre-authorization gate. Its output is a reviewed patch/release checklist, not a deployment approval.
