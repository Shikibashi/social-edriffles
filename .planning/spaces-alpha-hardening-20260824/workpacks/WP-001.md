# WP-001 — Fail-closed remote block checks

## Outcome

Protected follow request and approval operations never grant access when the actor’s current direct-block state cannot be completely established. A matching remote block after page one is recognized, while an unavailable or malformed remote collection produces no membership/approval mutation.

## Evidence and assumptions

- Current helper: `isDirectlyBlocked` in `upstream/atproto-pds/packages/pds/src/api/org/radlib/private/index.ts`.
- Current happy path is covered by `upstream/atproto-pds/packages/pds/tests/radlib-spaces.test.ts` for a requester hosted on another PDS.
- Current defect is first-page-only (`limit=100`) and fail-open on resolver/fetch/status/parse errors.
- The official block guidance describes server/client enforcement, but this fork’s protected access grant is application policy; the grant boundary must fail closed independently.

## Scope

- Replace the boolean remote lookup with an internal tri-state result: `blocked`, `not_blocked`, or `unknown`.
- Keep local backlink lookup as the fast path.
- For remote public block records, follow `cursor` pages until the matching subject is found or the collection is exhausted.
- Detect a repeated cursor, malformed page, resolver failure, fetch timeout, non-2xx response, and JSON/schema failure as `unknown`.
- Bound remote work to a 5-second total deadline and 20 pages of 100 records; reaching either bound before exhaustion is `unknown`.
- Map `unknown` to a generic fail-closed authorization error at the protected access-grant callers. Do not return successful `requested`/`approved` state and do not remove a member solely because lookup is unknown.
- Do not change ordinary public follows, standard block records, community-local ban semantics, or private record read paths in this workpack.

## Tests written first

Materialize these cases in the existing PDS integration test file before changing the helper:

1. A matching remote block on page two denies the protected follow request.
2. A matching remote block on page two denies protected approval.
3. A remote list response with a cursor is consumed until exhaustion and a complete negative lookup permits the existing requested/approved behavior.
4. Resolver failure, timeout, non-2xx, malformed JSON, missing `records`, repeated cursor, and page-budget exhaustion all fail closed with no membership or approval mutation.
5. The existing cross-PDS happy-path block test remains green.

Expected red result before implementation: the current helper either stops after page one or returns `false` on each failure, allowing at least the page-two and unavailable cases to proceed.

## Implementation

1. Add a small local result type/helper near `isDirectlyBlocked`; reuse the existing DID resolver and `getPdsEndpoint` path.
2. Preserve `redirect: 'error'`; add bounded abort handling and cursor query parameters.
3. Validate the minimum response shape before inspecting subjects; do not log block subjects or private authorization details.
4. Update `eitherDirectionBlocked` and both protected access-grant call sites to distinguish actual block from unknown.
5. Preserve the current `{state: 'blocked'}` result only for a confirmed block. Use the existing generic authorization error for unknown so the caller can retry without learning remote details.

## Acceptance

- The five new behavior cases and existing `radlib-spaces.test.ts` cases pass.
- `NODE_OPTIONS=--experimental-vm-modules pnpm --config.pm-on-fail=ignore --filter @atproto/pds exec jest tests/radlib-spaces.test.ts tests/space/auth.test.ts tests/space/records.test.ts tests/space/simplespace.test.ts --runInBand` passes.
- No test can observe a successful membership/approval mutation after an incomplete remote lookup.
- The helper does not perform more than 20 remote pages or exceed its total deadline.

## Risks and stop conditions

- Stop if the test harness cannot control remote pagination/failure deterministically; add a seam around the fetch/resolver rather than using live PDS data.
- Stop if an error mapping would disclose whether a remote actor has a block record.
- Stop if a proposed “temporary” cache of block state is introduced; this workpack does not authorize authorization-result caching.

## Handoff

This workpack unblocks WP-002 only after its source path is complete and focused tests are green. Handoff evidence is the exact test output plus a diff showing no changes outside the owned PDS API/test surface.
